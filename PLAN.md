# spotifast-themes — build plan

A community gallery of color themes for [Spotifast](https://github.com/crmne/spotifast). Everything lives in one GitHub repo. There is no server: themes are submitted through a GitHub issue form, a bot validates them and auto-merges the safe ones, and the gallery is a static Astro site deployed to GitHub Pages.

**Core goal: near-zero maintenance.** The owner should not need to review, merge, moderate, or update anything in normal operation. Every design choice below serves that goal. When in doubt, choose the option that needs less human attention.

**One exception: only the owner can remove or change a published theme.** Automation may add new themes; it never deletes or modifies existing ones on its own.

Build the phases in order. Each phase ends with its acceptance criteria passing.

---

## Ground truth: the Spotifast theme format

Source: https://spotifast.rocks/settings-and-files/#custom-themes. Do not invent fields.

```json
{
  "base": "dark",
  "colors": {
    "window": "#121212",
    "accent": "#1ed760"
  }
}
```

- `base`: `"dark"` (default) or `"light"`. Omitted colors inherit from that base palette.
- Supported color keys (exactly these 17): `window`, `panel`, `surface`, `surface_hover`, `surface_active`, `outline`, `text`, `secondary`, `dim`, `accent`, `accent_hover`, `on_accent`, `danger`, `warning`, `overlay`, `shadow`, `tint`.
- Values must be `#RRGGBB` or `#RRGGBBAA`.
- Spotifast accepts regular UTF-8 JSON up to 64 KiB. **This repo caps `theme.json` at 4 KiB** (a full theme is ~700 bytes).
- Users install by dropping the file in Spotifast's `themes` folder and running `spotifast reload-themes` (Linux picks it up automatically). The theme is listed by filename without `.json`.

Themes folder locations (for install instructions on the site):
- macOS: `~/Library/Application Support/me.paolino.spotifast/themes`
- Windows: `%APPDATA%\paolino\spotifast\config\themes`
- Linux: `~/.config/spotifast/themes`
- Everywhere: Settings → Appearance → Theme → "Open themes folder" button (recommend this first)

## Tech stack

- Node 22, TypeScript, pnpm
- Astro (static output) for the site
- Zod for schema validation
- `obscenity` (https://github.com/jo3-l/obscenity) for profanity filtering, using its English dataset and recommended transformers (catches leetspeak and spaced-out evasions)
- vitest for tests
- No runtime backend, no database, no analytics/telemetry
- **Pin every dependency to an exact version** (no `^` or `~`), commit the lockfile, and pin every GitHub Action to a full commit SHA. No Dependabot or Renovate.
- Pinning does not make CI immortal: GitHub retires the Node runtimes actions run on and deprecates old action versions (old `upload-pages-artifact` releases broke when artifact v3 was retired in early 2025). Use as few third-party actions as possible, and document in the README that the owner should expect roughly one maintenance pass per year to bump action SHAs.

### `meta.json` (written by the bot, never by submitters)

```json
{
  "name": "Stock Green",
  "github": "adamedwards",
  "tags": ["dark", "minimal"],
  "added": "2026-10-19",
  "issue": 12
}
```

There is **no free-text description field**. Free text is the main abuse surface; removing it eliminates most moderation work.

Rules:
- `name`: 3–30 chars, regex `^[A-Za-z0-9]+( [A-Za-z0-9]+)*$` (letters, numbers, single spaces). Must pass moderation (below). Unique case-insensitively. Becomes the download filename `<name>.json`.
- `github`: the submitting account's login, taken from the issue event, not from form input. Displayed as the author.
- `tags`: 0–4 values from an allowlist in `schema.ts`: `dark`, `light`, `minimal`, `vibrant`, `pastel`, `high-contrast`, `retro`, `warm`, `cool`, `monochrome`. `dark`/`light` must match `base`.
- `added`: ISO date. `issue`: submission issue number.
- Slug: derived from name (lowercase, spaces → `-`), unique.

### Moderation rules (`scripts/moderation.ts`)

A name is rejected if any of these match:
- `obscenity` matcher finds a match
- contains a blocked term (case-insensitive, **matched on word boundaries**): `spotify`, `spotifast`, `official`, `admin`, `moderator`, plus a small `BLOCKED_TERMS` array the owner can extend
  - do **not** strip all spaces before matching: that rejects innocent names like "Bad Minton" (→ "badminton" contains "admin")
  - to catch spaced-out evasions, collapse only runs of single-character words ("S P O T I F Y" → "SPOTIFY") and match that as a word too
- looks like a URL or handle: contains `www`, `http`, `com`, `net`, `org`, `io`, `gg` as a standalone word, or any digit-heavy string (more than 6 digits)

Unit-test this file heavily, including evasion cases and false-positive cases (e.g. "Bad Minton", "Cosmic Dusk" must pass).

## Phase 1 — repo, schema, validation

1. Init repo with pnpm workspace (root scripts + `site/`). Exact-version pins everywhere.
2. `scripts/schema.ts`: Zod schemas matching the rules above. `.strict()` everywhere so unknown keys fail.
3. `scripts/resolve.ts`: base default palettes for dark and light. Copy the real defaults from `Palette::dark()` and `Palette::light()` in `src/theme.rs` of crmne/spotifast (verified present as of v0.13.3), with a comment noting the source version. Export `resolveTheme(theme) => Record<ColorKey, string>`.
4. `scripts/contrast.ts`: WCAG 2.1 relative luminance + contrast ratio. Alpha colors are composited over `window` before measuring.
5. `scripts/moderation.ts` as above.
6. `scripts/validate.ts` checks, for every `themes/*/`:
   - exactly two files: `theme.json` and `meta.json`
   - valid UTF-8, no BOM; `theme.json` ≤ 4 KiB, `meta.json` ≤ 1 KiB
   - schemas pass, moderation passes
   - slug and name uniqueness
   - contrast on the resolved palette:
     - **error** if `text` on `window` < 4.5
     - **error** if `on_accent` on `accent` < 3.0 (WCAG non-text/large-text bar; Spotifast's own light default, `#ffffff` on `#15a64a`, is 3.19:1 and would fail a 4.5 rule)
     - **error** if `secondary` on `window` < 3.0
     - test: an empty light theme (`{"base":"light"}`) and an empty dark theme must both pass
   - near-duplicate check: **error** if every resolved color is within ΔE 2 (CIEDE2000) of an existing theme **or of one of Spotifast's 8 bundled palettes** (Catppuccin, Catppuccin Latte, Nord, Ristretto, Rose Pine, Rose Pine Dawn, Rose Pine Moon, Tokyo Night, shipped since 0.11.0). Store these as fixtures in `scripts/bundled-palettes/`. They are not in the crmne/spotifast repo as of v0.13.3; get the files from a fresh Spotifast install's themes folder. If they can't be obtained, skip this part with a `TODO`.
   - readable report; exits 1 on any error
7. Seed themes (committed directly by the owner, bypass the bot):
   - `stock-green`:
     ```json
     {
       "base": "dark",
       "colors": {
         "window": "#121212", "panel": "#000000", "surface": "#1f1f1f",
         "surface_hover": "#2a2a2a", "surface_active": "#333333", "outline": "#292929",
         "text": "#ffffff", "secondary": "#b3b3b3", "dim": "#7c7c7c",
         "accent": "#1ed760", "accent_hover": "#3be477", "on_accent": "#000000",
         "danger": "#f3727f", "warning": "#ffa42b",
         "overlay": "#000000b3", "shadow": "#00000080"
       }
     }
     ```
   - two more original themes (one dark, one light)
8. Unit tests for schema, contrast math, moderation, and validator edge cases (bad hex, unknown key, BOM, oversized file, duplicate name, near-duplicate palette, profanity evasions).

**Acceptance:** `pnpm validate` passes on seeds; every broken fixture in `scripts/__fixtures__/` fails with a clear message.

## Phase 2 — preview generator

The most important visual piece. No user screenshots; every preview is generated from the palette so they're consistent and always accurate.

`scripts/preview.ts` outputs `site/public/previews/<slug>.svg` at a 1200×750 viewBox.

Mock the Spotifast layout using only resolved theme colors:
- left sidebar (`panel`) with library label (`secondary`), 6 playlist rows with cover squares (`surface`) and names (`text`), one row highlighted (`surface_active`)
- main area (`window`) with a top fade from `tint` if set, playlist header (big title in `text`, meta in `secondary`), a large round play button (`accent` with `on_accent` icon)
- track list: 6 rows, row 3 in hover state (`surface_hover`), track numbers in `dim`, one "now playing" title in `accent`
- player bar across the bottom (`panel`) with cover, title/artist, transport controls, progress bar (filled `accent`, track `outline`), volume slider
- 1px dividers in `outline`
- a small badge in `warning` and a tiny dot in `danger` so those colors appear

Rules:
- Simple rounded rects and circles; system sans stack; short placeholder strings ("Liked Songs", "Daily Mix 1")
- Must look good. Spend real effort on spacing, radii (8px cards, 4px rows), proportions
- Deterministic output (same input → byte-identical SVG)

**Acceptance:** `pnpm previews` generates an SVG per theme; dark and light seeds both look correct in a browser.

## Phase 3 — gallery site

Astro static site in `site/`, reading `themes/*` at build time.

Pages:
- `/` — gallery grid
  - cards: preview SVG, name, `@github` author, 6 swatch dots (window, panel, surface, text, accent, secondary)
  - filter chips: All / Dark / Light, plus tags
  - client-side search by name/author/tag (small vanilla script, no framework)
  - sort: newest / name
- `/themes/<slug>/` — detail page
  - large preview
  - swatch table: key, hex, color chip, click to copy hex
  - **Download** button: serves `theme.json` as `<name>.json` (copy into `public/download/<slug>/<name>.json` at build, use `download` attribute)
  - **Copy JSON** button
  - install steps with OS tabs (mac / windows / linux), recommending "Open themes folder" first, then `spotifast reload-themes`
  - **Report** link → prefilled report issue form for this slug
- `/submit/` — link to the submission form, format summary, name rules, contrast rules, what happens automatically
- `/about/` — what this is; not affiliated with Spotify or Spotifast; link to Spotifast

Design:
- **Looks like a music app.** Borrow the familiar streaming-app layout: dark near-black background, left sidebar for navigation and filters, big header with a soft color fade, card grid of previews, rounded cards that lift on hover, a round green "play"-style accent button for Download. Use the layout language only, never Spotify's logo, name, wordmark or exact brand assets.
- **Plain, spoken copy.** Every bit of site text should sound natural read out loud: short sentences, everyday words, talk to the reader as "you". Say "Pick a theme, download it, drop it in your themes folder" rather than "Installation procedure". Same for the bot's issue comments and validation errors.
- Clean, dark-first, follows `prefers-color-scheme` with a manual toggle
- Mobile responsive, no horizontal scroll at 360px
- Previews are the hero; keep chrome minimal
- No trademarked logos or names
- Accessible: semantic HTML, focus states, alt text on previews ("Preview of <name> theme")

Config: `site` and `base` in `astro.config.mjs` set for `https://<user>.github.io/spotifast-themes/`, read from env so a custom domain is easy later.

**Acceptance:** `pnpm build` produces a static site; Lighthouse ≥ 95 on performance and accessibility; a downloaded file loads in Spotifast.

## Phase 4 — bot identity, CI and deploy

### Bot identity (required)

Events created with the default `GITHUB_TOKEN` do not trigger other workflows, so a PR the bot opens would never run validation and a merge would never deploy. Create a **GitHub App** (owner does this once; document the steps in README):
- permissions: Contents read/write, Pull requests read/write, Issues read/write
- installed only on this repo
- store `BOT_APP_ID` and `BOT_PRIVATE_KEY` as repo secrets
- every workflow that opens, merges, comments, or commits uses a token from `actions/create-github-app-token`

### Security rules (non-negotiable)

- **Never** use `pull_request_target` with a checkout of PR code
- Issue bodies are data only: parse as text, never execute, never interpolate into shell commands (pass via env vars / files)
- Least-privilege `permissions:` block on every workflow
- All actions pinned to commit SHAs

### `validate.yml`
- on `pull_request` and `push`
- pnpm install (cached), `pnpm test`, `pnpm validate`, `pnpm build`
- this is the required status check for merging

### `deploy.yml`
- on push to `main`
- build and deploy with the official Pages actions (`actions/configure-pages`, `actions/upload-pages-artifact`, `actions/deploy-pages`)
- permissions: `pages: write`, `id-token: write`, `contents: read`

### Repo settings (document in README; owner sets once)
- Branch protection on `main`: require `validate` to pass, allow auto-merge, squash only
- Disable blank issues
- Pages source: GitHub Actions
- Owner sets repo watch to "Ignore" or "Custom" so bot activity doesn't notify them

`PULL_REQUEST_TEMPLATE.md`: states that theme submissions should use the issue form; hand-made PRs are reviewed manually and may wait a long time.

**Acceptance:** a PR with a broken theme fails CI; merge to main deploys the site.

## Phase 5 — automated submissions and auto-merge

### `submit-theme.yml` (issue form)
Fields:
- Theme name (input, required)
- Tags (checkboxes from the allowlist; `dark`/`light` tags are set automatically from `base` in the JSON, not offered here)
- theme.json (textarea, `render: json`, required)
- Checkboxes (required): "I made this theme", "I release it under CC0", "I tested it in Spotifast"
- Auto-label: `theme-submission`

No description or other free-text fields. No separate base dropdown: `base` comes only from the JSON, so the two can never disagree.

### `submission.yml`
On `issues: [opened, edited]` with label `theme-submission`:
1. `issue-to-theme.ts` parses the form body (`### Label` sections), builds slug, writes `theme.json` + `meta.json` (github login from the event payload)
2. Run `validate.ts`
   - fail → comment the errors on the issue (one comment, updated in place), label `needs-fixes`, stop
3. Open or update a PR from branch `submission/<issue-number>` (using the App token), body `Closes #<n>`
4. Run `gate.ts`. **Auto-merge only if all are true:**
   - PR was created by the bot from this workflow (never auto-merge external PRs)
   - diff only **adds** `themes/<new-slug>/theme.json` and `themes/<new-slug>/meta.json`; no modifications, deletions, or other paths
   - file size caps and validation pass
   - submitter account is ≥ 30 days old (GitHub API `created_at`)
   - submitter has < 3 merged submissions in the last 24 hours
   - submitter is not in `BLOCKED_USERS` (a small array in `gate.ts`)
5. If the gate passes → enable auto-merge (squash) so it lands once `validate` passes. Comment on the issue: "Merged, live in a few minutes" with the theme URL.
6. If the gate fails on account age or rate limit → leave PR open, label `manual-review`, comment explaining it will be reviewed eventually. These are the only things that ever need a human, and it's fine if they sit.
7. Editing the issue re-runs and updates the same PR **only while the issue is open**. Edits to closed issues (already merged or rejected) are ignored, so a post-merge edit can't open a confusing duplicate PR.

### Community reports (`report-theme.yml` + `reports.yml`)
Report form fields: theme slug (input, prefilled from the site link), reason (dropdown: offensive name, copied theme, spam, other). Auto-label `theme-report`.

**Reports flag themes; only the owner removes them.**

`reports.yml` on `issues: [opened]` with label `theme-report`:
- `reports.ts` counts open report issues for that slug from **distinct** accounts that are ≥ 30 days old (same bar as submitters), excluding the theme's own author
- below threshold: label the report, leave it open, do nothing else
- at **3 distinct reporters**: bot opens a PR deleting `themes/<slug>/` that also appends to `removed.json` (slug, github, date, reason counts). It **never auto-merges this PR**: label it `needs-owner` and assign the owner. Merging it is the owner's one-click decision; closing it rejects the removal.
- when a removal PR merges, the bot closes all report issues for that slug with a comment

Owner shortcut: `reports.yml` also runs on `issue_comment: [created]`. If the comment is exactly `/remove` on a `theme-report` issue **and the commenter's login equals the repo owner** (from the event payload, not the comment text), the bot opens the removal PR and merges it immediately. Comments from anyone else are ignored.

- `removed.json` only ever changes through owner-approved removals, so a brigade can't get someone blocked
- a submitter with 2+ entries in `removed.json` is automatically treated as blocked by `gate.ts`

### Enforcing owner-only removal
- `.github/CODEOWNERS`: `/themes/ @<owner>` and `/removed.json @<owner>`
- branch protection: require code owner review, **but** the auto-merge path must still work for new submissions. Do this by bypassing the code-owner rule only for the bot App and having `gate.ts` refuse to enable auto-merge on any PR that modifies or deletes existing files. Net effect: additive bot PRs auto-merge; anything touching an existing theme needs the owner.
- verify this combination actually works in GitHub's branch protection / rulesets UI during Phase 4 and document the exact settings in the README. If the bypass can't be scoped that narrowly, fall back to: no code-owner rule, and rely on `gate.ts` + the bot only ever merging additive PRs.

**Acceptance:**
- valid submission from an eligible account → merged and live with no human action
- invalid submission → helpful comment, nothing merged
- new account or rate-limited → PR left with `manual-review`
- 3 distinct reports → removal PR opened, labeled `needs-owner`, **not merged**
- owner merges the removal PR, or comments `/remove` → theme removed and site redeploys
- `/remove` from any non-owner account → nothing happens

## Out of scope (don't build)

- Any server, database, accounts, likes/ratings, or analytics
- Free-text fields of any kind
- Changes to Spotifast itself
- User-uploaded screenshots
- Spotify logos or trademarked names
- Dependabot, Renovate, or anything that opens PRs on a schedule
